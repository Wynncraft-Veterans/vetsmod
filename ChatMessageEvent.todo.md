# ChatMessageEvent Migration — Replacing ChatLogMixin

## Overview

`ChatLogMixin` is a single `@Inject(at = HEAD, cancellable = true)` on `ChatComponent.addMessage(Component)` that serves as the mod's entire inbound chat pipeline. It handles seven distinct concerns in one monolithic method. Wynntils' `ChatMessageEvent` system can replace this mixin entirely, decomposing those concerns into focused event subscribers with proper chat classification for free.

---

## What ChatLogMixin Does Today

The mixin fires on every inbound chat message and runs the following pipeline in order:

1. **Logging** — `ChatLogger.logMessage(messageString)` writes every message to `vetsmod/debug.log` and relays to the VetsMod API.
2. **Mod-initiated command suppression** — If `GuildStateManager.isProcessingModGuildStats()` is true and the message matches guild stats patterns, or if `isProcessingModStaffRankCheck()` matches rank-check output, the message is cancelled (hidden from chat).
3. **Guild state detection** — `GuildStateManager.processMessage(message, messageString)` parses messages to detect guild name, rank, staff status, and the "Welcome to Wynncraft!" trigger.
4. **Staff outbound feedback suppression** — `StaffOutboundMessenger.shouldSuppressFeedback(messageString)` hides the `/msg` confirmation lines generated by `/v` fanout.
5. **Internal dispatch guard** — `ChatUtils.isInternalDispatch()` short-circuits to prevent re-processing of messages the mod itself injected via `displayClientMessage`.
6. **Bridge/Fruma dedup** — Parses guild chat format to extract `[username, message]`, records it in `BridgeMessageFetcher`, and suppresses server guild chat duplicates when Fruma mode is active.
7. **Chat rewriting** — Runs three rewriters in sequence:
   - `StaffGuildAlertRewriter.tryRewrite()` — ‼-prefixed guild messages → shout-styled alerts
   - `StaffChannelMessageRewriter.tryRewrite()` — 🔐-prefixed DMs → staff channel styled messages
   - `ServerGuildChatRewriter.tryRewrite()` — supporter guild chat → gradient pill styled messages

Each rewriter calls `ci.cancel()` and re-dispatches a rebuilt `Component` via `ChatUtils.dispatchToChat()` or `ChatUtils.dispatchAnimatedChat()`.

## What Wynntils Provides

### ChatHandler Pipeline

Wynntils' `ChatHandler` intercepts `SystemMessageEvent.ChatReceivedEvent` at `EventPriority.HIGHEST`. For every message it:

1. Converts the raw `Component` to `StyledText`
2. Classifies the message by testing against each `RecipientType`'s regex pattern
3. Posts `ChatMessageEvent.Match` — all listeners receive this, any can call `cancelChat()`
4. Posts `ChatMessageEvent.Edit` — listeners can call `setMessage(StyledText)` to rewrite content
5. Returns the (possibly null, possibly modified) message to the original MC method

### ChatMessageEvent.Match

```java
public static class Match extends ChatMessageEvent {
    private boolean chatCanceled = false;

    public StyledText getMessage()            // the classified message
    public MessageType getMessageType()       // FOREGROUND or BACKGROUND
    public RecipientType getRecipientType()   // INFO, GUILD, PRIVATE, etc.
    public void cancelChat()                  // suppress from display (all listeners still fire)
    public boolean isChatCanceled()
}
```

### ChatMessageEvent.Edit

```java
public static class Edit extends ChatMessageEvent {
    public StyledText getMessage()            // current (possibly already edited) message
    public void setMessage(StyledText msg)    // replace the displayed message
}
```

### RecipientType Enum (relevant values)

| Value | Matches |
|-------|---------|
| `GUILD` | Guild chat (PUA prefix `\uDAFF\uDFFC\uE006...`) and guild system messages |
| `PRIVATE` | Whisper/DM messages (PUA prefix + `\uE003` separator) |
| `INFO` | All other automated/system messages (fallback) |

### Registration

```java
WynntilsMod.registerEventListener(myListenerObject);
```

Any object with `@SubscribeEvent` methods is registered. Events fire on the render thread by default.

## Migration Plan

### Phase 1: Establish Event Listener Infrastructure

Create a new class that serves as the central Wynntils event listener for vetsmod. Register it during `VetsmodClient.onInitializeClient()` after `VetsConfig.load()` but before any fetcher starts.

```java
package org.wynnvets.chat;

import com.wynntils.core.WynntilsMod;
import net.neoforged.bus.api.EventPriority;
import net.neoforged.bus.api.SubscribeEvent;

public final class WynntilsChatListener {

    private static final WynntilsChatListener INSTANCE = new WynntilsChatListener();

    public static void register() {
        WynntilsMod.registerEventListener(INSTANCE);
    }

    // Event handlers go here (see Phase 2–5)
}
```

In `VetsmodClient.onInitializeClient()`:
```java
WynntilsChatListener.register();
```

#### Build dependency note

The `modCompileOnly "maven.modrinth:wynntils:v4.0.2-fabric"` dependency is sufficient. Since `wynntils` is a hard `depends` in `fabric.mod.json`, all Wynntils classes are on the runtime classpath. The NeoForge EventBus dependency (`net.neoforged.bus.api`) is already transitively available because Wynntils bundles (shadows) it into its JAR.

If the NeoForge EventBus annotations are not resolving at compile time, you may need to add a direct `compileOnly` on the eventbus JAR, or simply pull the `@SubscribeEvent` annotation class. Verify this compiles before going further.

### Phase 2: Migrate Chat Logging (Concern #1)

**Current**: First line of `ChatLogMixin.onChatMessage()` calls `ChatLogger.logMessage(messageString)`.

**New**: Subscribe to `ChatMessageEvent.Match` at `HIGHEST` priority (runs before any other vetsmod listener). This ensures every classified message is logged regardless of whether it's later cancelled.

```java
@SubscribeEvent(priority = EventPriority.HIGHEST)
public void onChatLog(ChatMessageEvent.Match event) {
    ChatLogger.logMessage(event.getMessage().getStringWithoutFormatting());
}
```

**Why HIGHEST**: Logging must happen before any cancel/suppress logic. Wynntils guarantees all `Match` listeners fire even if another listener calls `cancelChat()`, so logging always happens.

**Consideration**: `ChatLogger.logMessage()` currently receives the raw `Component.getString()` which includes `§` formatting codes. `StyledText.getStringWithoutFormatting()` strips them. If the log file should preserve formatting codes for debugging, use `event.getMessage().getString()` instead (which returns `§`-coded text).

---

### Phase 3: Migrate Mod-Initiated Suppression (Concerns #2, #4)

**Current**: Guild stats output and staff rank check output are matched by string patterns and suppressed. Staff outbound `/msg` feedback is matched by `StaffOutboundMessenger.shouldSuppressFeedback()`.

**Problem**: These messages arrive as `RecipientType.INFO` or `RecipientType.GAME_MESSAGE`. They are system responses to commands the mod sent silently. The Wynntils `Match` event fires for them with full `StyledText` content.

**New**: Subscribe at `HIGH` priority (after logging, before rewriters):

```java
@SubscribeEvent(priority = EventPriority.HIGH)
public void onSuppressModOutput(ChatMessageEvent.Match event) {
    String text = event.getMessage().getStringWithoutFormatting();

    // Suppress guild stats output from mod-initiated /guild stats
    if (GuildStateManager.isProcessingModGuildStats() && isGuildStatsMessage(text)) {
        GuildStateManager.processMessage(text);  // still extract state
        event.cancelChat();
        return;
    }

    // Suppress /gu rank check output
    if (GuildStateManager.isProcessingModStaffRankCheck() && isStaffRankCheckMessage(text)) {
        GuildStateManager.processMessage(text);
        event.cancelChat();
        return;
    }

    // Suppress /msg feedback from /v staff fanout
    if (StaffOutboundMessenger.shouldSuppressFeedback(text)) {
        event.cancelChat();
        return;
    }
}
```

Move the `isGuildStatsMessage()` and `isStaffRankCheckMessage()` methods from `ChatLogMixin` into `GuildStateManager` (they belong there conceptually).

**Important**: `cancelChat()` does NOT prevent other `Match` listeners from firing — it only marks the message for suppression from the chat HUD. This is exactly what we want: logging still happens, but the message won't display.

### Phase 4: Migrate Guild State Detection (Concern #3)

**Current**: `GuildStateManager.processMessage(message, messageString)` is called on every message to detect "Welcome to Wynncraft!", guild name, guild rank, etc.

**Better approach**: This is a separate concern from the chat pipeline. It should be its own listener:

```java
@SubscribeEvent(priority = EventPriority.HIGH)
public void onGuildStateDetection(ChatMessageEvent.Match event) {
    GuildStateManager.processMessage(
        event.getMessage().getComponent(),
        event.getMessage().getStringWithoutFormatting()
    );
}
```

**Even better (future)**: Replace `GuildStateManager.processMessage()` entirely with:
- `Models.Guild.getGuildName()` / `Models.Guild.getGuildRank()` / `Models.Guild.isInGuild()` for guild membership (eliminates `/guild stats` parsing)
- `WorldStateEvent` for "Welcome to Wynncraft!" detection (eliminates chat scanning)
- `GuildEvent.Joined` / `GuildEvent.Left` for guild change tracking

This is out of scope for this migration (it's a separate opportunity) but should be noted — once `Models.Guild` replaces the manual detection, the guild-stats suppression logic in Phase 3 also disappears entirely.

---

### Phase 5: Migrate Internal Dispatch Guard and Rewriters (Concerns #5, #6, #7)

**Current**: The mixin checks `ChatUtils.isInternalDispatch()` to avoid re-processing its own injected messages, then runs three rewriters, each of which may `ci.cancel()` and re-dispatch.

**Key architectural question**: When vetsmod calls `ChatUtils.dispatchToChat()`, which calls `minecraft.player.displayClientMessage()`, does Wynntils' `ChatHandler` intercept that re-dispatch?

**Answer**: Yes. `displayClientMessage` internally calls `ChatComponent.addMessage()`, which fires `SystemMessageEvent.ChatReceivedEvent`, which Wynntils intercepts. **This means the internal-dispatch guard is still needed** — but it can be checked inside the event listener instead of a mixin.

**New** — subscribe at `NORMAL` priority for rewriting:

```java
@SubscribeEvent
public void onChatRewrite(ChatMessageEvent.Match event) {
    // Don't rewrite our own re-dispatched messages
    if (ChatUtils.isInternalDispatch()) {
        return;
    }

    String messageString = event.getMessage().getStringWithoutFormatting();
    // We need the original Component for rewriters that inspect Style/Color info
    Component component = event.getMessage().getComponent();

    // Bridge/Fruma dedup (concern #6)
    String[] parsedGuildChat = parseGuildChat(messageString);
    if (parsedGuildChat != null) {
        BridgeMessageFetcher.recordServerGuildMessage(parsedGuildChat[0], parsedGuildChat[1]);

        if (BridgeMessageFetcher.isFrumaModeEnabled()
            && BridgeMessageFetcher.wasBridgeMessageRecentlyDisplayed(
                parsedGuildChat[0], parsedGuildChat[1])) {
            event.cancelChat();
            return;
        }
    }

    // Staff guild alert rewriter
    if (StaffGuildAlertRewriter.tryRewrite(messageString)) {
        event.cancelChat();
        return;
    }

    // Staff channel message rewriter
    if (StaffChannelMessageRewriter.tryRewrite(component, messageString)) {
        event.cancelChat();
        return;
    }

    // Supporter gradient pill rewriter
    if (ServerGuildChatRewriter.tryRewrite(component, messageString)) {
        event.cancelChat();
    }
}
```

#### Leveraging RecipientType for Targeted Rewriting

Currently all three rewriters do their own format detection (parsing PUA glyphs to figure out if it's guild chat, parsing `\uE003` for private messages, etc.). With `ChatMessageEvent`, you get `RecipientType` for free:

```java
@SubscribeEvent
public void onChatRewrite(ChatMessageEvent.Match event) {
    if (ChatUtils.isInternalDispatch()) return;

    RecipientType type = event.getRecipientType();
    String text = event.getMessage().getStringWithoutFormatting();
    Component component = event.getMessage().getComponent();

    switch (type) {
        case GUILD -> {
            // Bridge dedup
            String[] parsed = parseGuildChat(text);
            if (parsed != null) {
                BridgeMessageFetcher.recordServerGuildMessage(parsed[0], parsed[1]);
                if (BridgeMessageFetcher.isFrumaModeEnabled()
                    && BridgeMessageFetcher.wasBridgeMessageRecentlyDisplayed(parsed[0], parsed[1])) {
                    event.cancelChat();
                    return;
                }
            }
            // Staff alert (‼ prefix) — only valid in guild chat from staff
            if (StaffGuildAlertRewriter.tryRewrite(text)) {
                event.cancelChat();
                return;
            }
            // Supporter gradient pill — only valid for guild chat
            if (ServerGuildChatRewriter.tryRewrite(component, text)) {
                event.cancelChat();
            }
        }
        case PRIVATE -> {
            // Staff channel (🔐 prefix in DMs) — only valid for private messages
            if (StaffChannelMessageRewriter.tryRewrite(component, text)) {
                event.cancelChat();
            }
        }
        default -> {
            // No rewriting for other message types
        }
    }
}
```

**This is a significant improvement**: instead of every rewriter independently running expensive regex/glyph parsing on every single chat message, the type switch ensures each rewriter only runs against messages of the correct type. `StaffChannelMessageRewriter` no longer wastes cycles checking every guild chat for `\uE003`, and `ServerGuildChatRewriter` never inspects private messages.

---

### Phase 6: Move parseGuildChat to a Shared Location

The `parseGuildChat()` private method currently lives in `ChatLogMixin`. It parses the PUA-glyph rank indicator + colon to extract `[username, message]` from guild chat. Move it to `ChatUtils` or a new `GuildChatParser` utility class so both the new `WynntilsChatListener` and `StaffGuildAlertRewriter`/`ServerGuildChatRewriter` (which have their own copies) can share it.

`StaffGuildAlertRewriter` and `ServerGuildChatRewriter` each contain their own `parseGuildChat()` method with slightly different implementations — all three should be unified.

---

### Phase 7: Delete ChatLogMixin

Once all concerns are migrated to `WynntilsChatListener`:

1. Remove `ChatLogMixin.java` from `src/client/java/org/wynnvets/mixin/client/`
2. Remove the `"ChatLogMixin"` entry from `src/client/resources/vetsmod.client.mixins.json`
3. Verify the mod builds and tests pass

## Ordering / Priority Summary

| Priority | Listener | Concern |
|----------|----------|---------|
| `HIGHEST` | `onChatLog` | Logging (always fires, even on cancelled messages) |
| `HIGH` | `onSuppressModOutput` | Suppress mod-initiated command output |
| `HIGH` | `onGuildStateDetection` | Guild state machine processing |
| `NORMAL` | `onChatRewrite` | Bridge dedup, alert/channel/gradient rewriting |

These can all be methods on a single `WynntilsChatListener` class. Priority ordering within the same class is determined by the `@SubscribeEvent(priority = ...)` annotation.

## Edge Cases and Risks

### 1. Message Format Differences: Component vs StyledText

**Risk**: The rewriters (`ServerGuildChatRewriter`, `StaffChannelMessageRewriter`) inspect `Component` sibling structure, `Style` objects, and `TextColor` values. `ChatMessageEvent` provides `StyledText`, not `Component`.

**Mitigation**: `StyledText.getComponent()` reconstructs a `MutableComponent` from the `StyledText`. However, the reconstructed component may not exactly match the original Component's sibling tree structure (it may flatten nested siblings). Test whether `event.getMessage().getComponent()` preserves enough structural information for the rewriters.

**If it doesn't**: The rewriters need refactoring to work with `StyledText` directly (using `.getMatcher()` and `.getString()` instead of Component tree walking). This is a larger undertaking but produces more robust code.

### 2. Mod-Injected Messages Reaching Wynntils

**Risk**: When vetsmod calls `ChatUtils.dispatchToChat()` → `displayClientMessage()`, Wynntils' `ChatHandler` will intercept it, classify it, and fire `ChatMessageEvent` for it. The `isInternalDispatch()` guard prevents re-processing, but Wynntils still classifies and potentially transforms the message.

**Mitigation**: Messages dispatched by vetsmod are complete, fully-formatted Components. Wynntils will classify them (likely as `GUILD` if they contain guild prefix glyphs) and fire Match/Edit events, but since no vetsmod listener modifies them (internal dispatch guard), they pass through. This should be fine, but **test** that Wynntils' own features (e.g., chat tab filtering) don't hide vetsmod-reconstructed messages.

### 3. Event Bus Dependency

**Risk**: Wynntils uses NeoForge's EventBus (`net.neoforged.bus.api`) which it JiJ's (Jar-in-Jar includes) into its Fabric build. The `@SubscribeEvent` annotation and `EventPriority` enum need to be available at compile time.

**Mitigation**: Since `modCompileOnly` already provides Wynntils on the compile classpath, and Wynntils bundles the eventbus, the annotation should resolve. If not, add an explicit `compileOnly` for the NeoForge EventBus artifact:
```groovy
compileOnly "net.neoforged:bus:8.0.2"
```
(Check the exact version in Wynntils' `gradle.properties`.)

### 4. Timing: When Are Events Available?

**Risk**: `WynntilsMod.registerEventListener()` must be called after Wynntils has initialized its event bus. If vetsmod's `ClientModInitializer.onInitializeClient()` runs before Wynntils init, the call may fail.

**Mitigation**: Fabric loads mods in dependency order. Since `wynntils` is declared as a `depends` in `fabric.mod.json`, Fabric will initialize Wynntils before vetsmod. By the time `VetsmodClient.onInitializeClient()` runs, Wynntils' event bus is ready.

### 5. cancelChat() vs ci.cancel() Semantics

**Risk**: In the mixin, `ci.cancel()` prevents `ChatComponent.addMessage()` from executing, so the message never enters the chat HUD. With `ChatMessageEvent.Match`, `cancelChat()` sets a flag that `ChatHandler` checks — if flagged, `ChatHandler` returns `null` to the MC method, which achieves the same suppression. However, if another listener (a Wynntils feature) calls `cancelChat()` on a message that vetsmod needs to process, vetsmod's rewriter still fires (the Match event delivers to all listeners regardless of cancellation). This is the correct behavior — but verify that Wynntils' own features don't cancel GUILD messages that vetsmod needs.

### 6. AnimatedGradientSequence Dispatch

**Risk**: `ServerGuildChatRewriter` dispatches via `ChatUtils.dispatchAnimatedChat()`, which wraps lines in `AnimatedGradientSequence` during the `displayClientMessage` call. The AnimatedChatMixin (a separate mixin on `ChatComponent.addMessageToDisplayQueue`) picks this up. This flow is independent of the ChatLogMixin and should continue to work after migration.

**No change needed** for `AnimatedChatMixin` — it's a rendering concern, not a chat classification concern.
