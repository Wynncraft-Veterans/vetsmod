# vetsmod Retro Textures

`/wv retro on` draws Wynncraft in 2013 Minecraft art. Blocks, items and mobs get Programmer Art; the blocks Wynncraft adds with no vanilla equivalent (its dark stone, molten rock) are 2013 art tinted to match, and those with one (Sky Wood, the oak log) are that block's art; each weapon class, armour piece, tool, key, meal, material, powder, rune and ward shows as one vanilla item; potions are vanilla bottles of their family's colour; worn armour is vanilla's; containers, tooltips and a few Wynntils panels look like vanilla's. Nothing Mojang or Wynncraft made is shipped: each client builds the pack in memory from its own game files, from rules in two YAML files that key on texture ids and model paths (never custom model data, which churns). While the pack is drawn, a semantic layer draws over the screens what no pack can say (plain container titles, Wynncraft's own background under screens whose art it keeps, glass slots, no attack-speed effect, a gear box's type) and draws vanilla's HUD from Wynncraft's values. While retro is on, four Wynntils settings are switched and later put back. A player can turn any part of this off on its own, or keep only one: `/wv retro only weapons` (§13).

**Division of labour.** The two YAML files own the rows and the reason for each; this document does not list them. It owns the mechanisms, the invariants, the package map, a recipe for each known pattern (§11) and the burdens that outlast a change (§12).

Accepted package cycles, every pair of retro's packages that import each other:

- `retro.manifest` imports `retro.rules.RetroAssetIds` (a pure id class) while `rules` imports `manifest`.
- `retro.pack` and `retro.pack.generate` call each other: the injector builds the generator, the steps use `PackFiles`.
- `retro` and `retro.pack`: `RetroModeManager` and `RetroCommands` use `RetroPackInjector`, and the injector and `RetroPackResources` report to `RetroModeManager`. `pack.generate` also imports `retro` (`RetroPackGenerator` records its `RetroReport`), which closes `retro`, `pack`, `pack.generate`.
- `retro` and `listeners`: `RetroModeManager` asks `ServerConnectionListener`, and `WynntilsEventListener` latches `RetroModeManager`.
- `retro.render` and `listeners`: `RetroHud` asks `ServerConnectionListener`, and the `Retro*Listener` classes call `retro.render`.

## 1. Invariants

A change to retro keeps these.

1. **Nothing throws into a reload.** Every entry point of the pack and of the drawing code catches and answers as if retro were absent (§2).
2. **Generation is lazy and runs on the reload's workers**, never the render thread; the injector does no work (§2).
3. **Folder gate.** A request outside `textures/`, `models/`, `items/` and `equipment/` generates nothing.
4. **Only the player's own game files go in.** Every generated byte is computed from the client's Programmer Art, vanilla and Wynncraft packs; the jar ships only vetsmod originals (models, blank textures).
5. **Rules key on texture ids and model paths**, never on custom model data.
6. **One atlas per item model.** A stub's art and its parent come from one atlas, and a stub is written only when everything it names resolves (§5).
7. **Everything drawn over Wynncraft's art gates on `RetroModeManager.isPartLive(<its part>)`**, and what a mixin does on every server on `isPartLiveOnWynncraft(<its part>)`; the `retro/render` classes draw through a `RetroGuard` (§7, §13).
8. **A failure latches for the session.** A failed generation or reload, or Wynntils listeners that cannot register, sets the latch; the setting is left alone and the next launch tries again (see Latch under Placement and lifecycle).
9. **Ids belong in `RetroAssetIds`.** A generated id is spelled once there, and the parser, rules, generator and drawing code share it.
10. **No static initialiser touches Wynntils or Minecraft**, so pure logic stays unit-testable (§10). The seams are `PackFacts`, `WynntilsSettings` and the `Pixels` image type.
11. **A row key a section does not have fails the parse**, and so does a repeated section or key; a section name nobody knows is ignored with a debug line and the real-file tests reject it, so a typo fails the build.

### Placement and lifecycle

`createReload` is where a reload's pack list becomes the resource manager, and the only place a pack can go above a server pack, which Minecraft fixes at the top of the list the player sees. `RetroPackInjector.inject` (called from `RetroResourceReloadMixin`) puts `RetroPackResources` (id `vetsmod/retro`) directly above the highest Wynncraft pack: one whose id starts with `server/` (the first session after a pack update) or `wynntils_preloaded/` (every other), confirmed by a content probe (`minecraft:font/banner/box.json`), so another server's pack is never taken for Wynncraft's.

A reload gets no retro pack when retro is off or latched, when it has no Wynncraft pack, or when it is Minecraft's recovery reload (the previous reload's `done()` completed exceptionally). Mod resources sit below Wynncraft, so only `vetsmod:` assets in the jar can help the generated files; that is why the stub parents and blanks live there.

**Live flag.** `RetroModeManager.isPackLive()` turns true only when a reload with a non-empty retro pack finishes, and every reload clears it as it starts. Reload numbers keep a reload that finishes late from marking a later one live. `isLiveOnWynncraft()` adds "the game is on Wynncraft" (Wynntils' `ServerConnectionListener`), because the pack stays live in singleplayer with Wynntils' preloaded copy of Wynncraft's pack still loaded. Code reached through a Wynntils event, which fires only on Wynncraft, asks `isPackLive()`; a mixin that runs on every server asks `isLiveOnWynncraft()`: the hovered slot, the effects list, the item model, and the container background.

**Latch.** A failed reload makes Minecraft deselect every resource pack and save `options.txt`, so a retro failure must never cause one and must not happen twice. A failed generation, a failed reload with a non-empty retro pack in it, or retro's Wynntils listeners failing to register (`WynntilsEventListener.register`, since a retro with some of them would keep its pack and HUD but not hide Wynncraft's bars or draw its glass) sets the latch (`RetroModeManager.latch`): one warning, one red chat line, no retro pack in any later reload until the game restarts, and the Wynntils settings retro changed go back.

## 2. Threads and the no-throw rule

`createReload` runs on the render thread and starts every reload listener there. So the injector inserts a declared-but-empty pack with fixed namespaces (`minecraft`, `wynntils`, `avomod2`, `vetsmod`) and fixed folders (`textures`, `models`, `items`, `equipment` generated; `lang` static), no `pack.mcmeta` and no filter.

- **Folder gate.** Vanilla's `FontManager.prepare` lists `font/` synchronously on the render thread before the loading screen exists, and the resource manager asks every pack; without the gate that request ran the whole generation there. A new generated folder joins `RetroPackResources.FOLDERS` only after checking that nothing reads it on the render thread before the reload's preparations finish. `equipment/` (`EquipmentAssetManager`) and `items/` (`ClientItemInfoLoader`) are read on workers.
- **Static files.** `lang/` is read on the render thread, so a second supplier, `RetroPackGenerator.staticFiles`, answers it from the rule files alone, memoised under its own lock. A failed generation takes the static files with it; a failed read of them empties the pack before it generates. Both latch.
- **Lazy, memoised generation.** The first request inside the generated folders comes from a worker (the atlas, model, item definition and equipment loaders) and runs the generator inline under a lock; later requests and any that waited get the same files. A texture the render thread loads for the first time while a worker generates (a skin) waits on the lock.
- **No throw.** `getResource`, `listResources` and every supplier catch `Throwable` and answer as if the file were absent; the first failure logs at warn, later ones at debug. `RetroPackResources` catches around the generator, which catches nothing of its own: what a step throws outside `PackOutput.attempt` empties the pack for the pack's life and latches. A step wraps each row in `attempt`, so a file it cannot read, or a rule it cannot apply, is skipped and listed in the report rather than failing the generation.
- **Close.** `close()` drops the files; a generation still running at close drops its result.

## 3. The rule files

The files follow `definitions.yml`'s conventions: header bullets, whole-id Java regexes, quoted entries, SnakeYAML safe load. Their headers give each section's format and a new row's shape. This table says what each section reads and which class acts on it.

| Section | Decides | Acts in |
|---|---|---|
| `parts` | which part of retro owns an id, so the player can turn it off (§13) | `PartFilter`, then every step and drawing class it gates |
| `sources`, `keep_wynncraft`, `tints`, `aliases`, `same_name`, `layer_groups` | which texture is written and from what (§4) | `TextureRules`, `TextureStep` |
| `image_edits` | rectangles painted over a copy or tint (§6) | `TextureStep`, `PixelDrawing` |
| `item_models`, `retro_ingredients.yml` | the stub that replaces an item model (§5) | `ModelRules`, `ModelStubStep` |
| `recipes`, `materials`, `content_book_activities`, `potions` | many `item_models`, `potions` and `source_copies` rows from a few lines (§5) | `ItemTables`; `ModelStubStep` and `SourceCopyStep` write them |
| `equipment` | worn armour (§5) | `EquipmentStep` |
| `wynncraft_copies`, `source_copies`, `wynntils_textures`, `blank_textures`, `lang` | extra files (§6) | `WynncraftCopyStep`, `SourceCopyStep`, `WynntilsTextureStep`, `BlankTextureStep`; `lang` through `RetroPackGenerator.staticFiles` |
| `outlined_icons`, `accessory_tiers`, `block_models` | generated items and block models (§5) | `OutlinedIconStep`, `AccessoryTierStep`, `BlockModelStep` |
| `container_titles`, `glyph_titles`, `slot_fills`, `slot_values`, `stack_models`, `hidden_inventory_effects` | what is drawn over the screens (§7); no files | the `retro/render` classes |
| `gear_box_icons` | the item drawn over a gear box (§7); also has the pack copy vanilla's item definition of each item | `RetroSlotIcons`, `ItemDefinitionStep` |
| `wynntils_config` | the Wynntils settings switched while retro is on (§7) | `WynntilsConfigOverrides` |

`RetroModeManager.manifest()` parses the files once a session (they ship in the jar) and stands an empty manifest in, with one warning, when they cannot be read. A family's sections live in one file, each name one constant: to add a section, add its constant and put it in the family's `NAMES`, `parse`, `addCounts` and component list. `ManifestYaml` has the row walkers: `patternRows` (first-match pattern rows), `idRows` (literal-id keys), `typeRows` (Wynntils type names), `textRows` (any key), `listRows` (a list of mappings, with the keys a row may have).

**Sources** (`sources`, `RetroSource`). Per texture pattern, the packs a texture is read from, most preferred first; the first listed pack that has it supplies it. `programmer_art` is the client's built-in pack, which the generator opens and closes; `vanilla` is the client's own textures, shared and never closed. A missing source simply has no textures. Entities and the villagers' layers come from one source; `gui/` reads vanilla only (Programmer Art's few GUI files would mix two looks). **A copied PNG carries the `.mcmeta` beside its source**, because Minecraft takes a texture's `.mcmeta` only from the pack that provides the PNG or a higher one; this keeps nine-slice sprites and animated strips right. A `same_name` copy from vanilla of a texture Wynncraft does not ship is left out (`UNCHANGED`): it would change nothing, or override a pack the player chose.

## 4. Texture precedence

A texture is decided by the first of these that applies, whether or not Wynncraft ships it (`TextureRules.decide`):

1. `keep_wynncraft`: Wynncraft's stays (its blanks, repurposed names, animated sponges, worn copper armour).
2. `tints`: a source's texture, tinted, is written in its place. When no source has the texture it starts from, or the texture it matches, Wynncraft's stays and the rules below are not tried.
3. `aliases`: another texture is copied in. When no source has the target, Wynncraft's stays and `same_name` is not tried.
4. `same_name`: the texture of the same id is copied in, when a source has it.
5. Wynncraft ships it fully transparent: a deliberate blank, kept.
6. Otherwise Wynncraft's stays (or the lower packs' when Wynncraft ships none).

Then `layer_groups` turns a group's copies and tints back into keeps unless every member Wynncraft ships is copied or tinted, all from one source (a layered model draws one source's textures). Rule 5 ranks below the explicit rules because Wynncraft blanks the HUD sprites retro restores. Rules 5 and 6 emit the same nothing, so the generator never decodes an image to tell them apart: its `PackFacts` answers "transparent" with `false`, and the report counts both as `no_rule`.

**Tints.** A tint is a source's texture with each channel multiplied by a factor (`TintFactors`, `Recolours.tint`), written at the texture's own id with the `.mcmeta` beside the source. A row names the texture it starts from (`source`, the texture itself without one; it and a `match` texture are read through the `sources` rows as a copy is) and how each channel's factor is found:

- `'#RRGGBB'`: the colour's channel over 255, as Minecraft's own tints multiply;
- `{match: <texture>}`: that texture's mean over the source's;
- `{relative_to: <texture>}`: the mean of Wynncraft's live copy of the texture over the mean of Wynncraft's live `<texture>`, so the source changes as Wynncraft changed its texture from that one;
- `auto`: Wynncraft's live mean over the source's;
- `{like: <texture>}`: exactly the change the row matching that texture makes to it: that row's factors at its strength, then its contrast around that texture's tinted mean. A pixel the source shares with the texture comes out as it does there, which a `match` or the row's own contrast cannot do. The texture is a literal id, exactly one row must match it, that row may not be a `like` (no chains), and a `like` row has no `strength` or `contrast` of its own.

"Live" is what the reload shows without retro: Wynncraft's texture, or vanilla's where it ships none. `strength` (0 to 1) applies part of the change, `factor = 1 + strength × (ratio − 1)`. Means count the visible pixels only, and the multiply stops each channel at 255 and keeps alpha. `contrast` (default 1) then moves each visible pixel's channels toward the tinted image's mean, `mean + contrast × (channel − mean)`, so the colour the factors gave stays the mean while the texture grows calmer; a row can have a `contrast` and no `tint`. A tint whose images are missing or fully transparent, or whose divisor has a channel of 0, is skipped and reported. One factor per channel cannot tint a two-tone texture apart. A tint keeps the image's size and its source's `.mcmeta`, so an animated source stays animated.

**Aliases** send many textures to one, such as the six-sided piston: every face any piston model draws becomes the piston's plank face, so no model is edited. Wynncraft's pistons are crates drawn through vanilla's `piston` blockstate and its own `sticky_piston` blockstate; the rows name every texture those models use.

## 5. Item models, ingredients, worn armour, generated items

Wynncraft's `items/*.json` never merge and are never copied; the generator overrides the **models they point at** with small stubs: Wynncraft's under `item/wynn/`, Avomod's that a `potions` row names, and the block models `block_models` names. So `oak_boat.json` and the `w<N>` models Wynntils reads are never touched. `ModelRules.modelStub` picks the rule: a model under `item/wynn/ingredient/` by its stem's row in `retro_ingredients.yml` if it has one (`keep` leaves Wynncraft's); with no row, and for any other model, the first `potions` row that matches, failing that the first `item_models` row. Table rows (`ItemTables`) come before `item_models`' own, and each is a literal model id that matches one row only.

- **One atlas per model.** An item model that mixes atlases fails to bake ("Multiple atlases used in model"), and one failure sends Wynncraft's whole `items/potion.json` to the missing model. A stub's art and its parent's blank share the art's atlas (`item/` or `block/`), a row whose texture is in neither is refused, and a stub is emitted only when every texture and model it names resolves.
- **Tint-proof parents.** Weapon and tool stacks carry a non-white potion colour on tint index 0, and armour stacks their dye, so a texture stub parents `vetsmod:item/retro/tint_proof_<kind>_<atlas>`: `layer0` a fully transparent blank from that atlas, `layer1` the art, which no tint reaches. `ParentKind` (`handheld`, `handheld_rod`, `bow`, `generated`) picks the vanilla model that positions the item.
- **Model stubs.** A row with a `model` stubs the model with `{"parent": "<model>"}` and nothing else, the ingredients' form: the stack's colour then tints that vanilla model as it tints the vanilla item. It is for a Wynncraft model whose one tint is the one vanilla's model takes, or for one of vetsmod's own under `vetsmod:item/retro/`.
- **Potions** (`potions`). Wynncraft's `item/wynn/potion/<family>_<empty|half|full>` and Avomod's own models become the vanilla potion: `ItemTables` makes a `source_copies` row per family, the `potion_overlay` recipe in the family's colour at `RetroAssetIds.potionLiquid` (`vetsmod:item/retro/potion/<family>`), and the stub parents `vetsmod:item/retro/tinted_potion` (layer 0 the item blank, which takes the stack's colour; layer 1 the liquid; layer 2 the bottle). All three fills are the full vanilla potion, because Wynncraft draws each full of liquid.
- **Ingredients** carry a white tint, so their stubs are `{"parent": "minecraft:item/<x>"}`. Almost every stem already parents a vanilla model whose textures `same_name` replaces, so `retro_ingredients.yml` covers only the stems whose model parents neither, and the rest fall to `potions` and `item_models`.
- **Tables** (`recipes`, `materials`, `content_book_activities`). A `Recipe` is a way one piece of art takes a colour: multiply (`Recolours.tint`), scale a `scale_from` colour to the asked one (can lighten), or `hue_of` (only the pixels of one hue, for art with grey to keep). Scale and multiply (`Recolours.Outline`) leave near-grey dark pixels (an outline) undyed, below `outlineCutoff`; hue rows pass over grey. The potion overlay has no such pixel, so a potion's liquid is its colour all over. `scale_from` is read against the art's first source. A `materials` family names its models prefix, the vanilla art each name draws, and under a recipe's name the names that are that recipe's art in a colour; each becomes a `source_copies` row (`vetsmod:item/retro/material/<family>_<name>`) and an `item_models` row. `content_book_activities` makes each activity's states likewise; the tracked state's `scale_from` (`#808080`) is a brightness factor, deliberately absent from the art.
- **Gear box chest.** Every unidentified gear box is `vetsmod:item/retro/chest`: 1.21.11's `ChestModel` as three block-model elements (`template_retro_chest`, every face's `uv` solved against Minecraft's `FaceInfo` vertex order), held as vanilla's chest item is, drawing a `source_copies` copy of `entity/chest/normal` in the blocks atlas. The type is drawn over it in the GUI (§7).
- **Worn armour** (`equipment`). Armour on a stand or another mob is drawn from its `equippable` asset (`textures/entity/equipment/<layer>/<texture>.png`, dyed when the layer is dyeable). Wynncraft's 24 assets make every layer dyeable and give its own materials textures of their own names, so a texture rule alone cannot draw them as vanilla's. A row maps an asset id to a vanilla asset, or `keep`; for each mapped asset the generator writes vanilla's `equipment/<target>.json` byte for byte under Wynncraft's id, and `same_name`'s `entity/` row gives the textures their 2013 art. An asset no row matches keeps its file; a player's own armour uses `minecraft:hidden`, a blank.
- **Armour icons.** Every Wynncraft armour stack is a leather item whose dye tints the leaf model. Gold, chainmail, iron, diamond and netherite show the vanilla piece on the tint-proof parent; titanium shows netherite; leather and `pale_leather` are model stubs of `minecraft:item/leather_<piece>`, so the piece takes the dye and its overlay stays undyed.
- **Accessory tiers** (`accessory_tiers`). Rings, bracelets and necklaces show their level as armour does. Every accessory of a type is drawn from one texture of Wynncraft's, redrawn in the tier's colour ramp by its luma (`Recolours.ramp`), except pixels darker than `outline_below_luma`, which become the grey of their luma. `AccessoryTierStep` writes each type and tier as a texture, a model and an item definition (`GeneratedItemWriter`) at `RetroAssetIds.accessoryPath`, plus `<type>_empty`, the art's edge and the inner pixels darker than `empty_lines_below_luma`, in `empty_outline`'s colour (`PixelDrawing.edge`), for an empty accessory slot (`item_models` points Wynncraft's slot placeholder at it). `RetroAccessories` answers the per-stack hook from Wynntils' `GearTypeItemProperty` and `LeveledItemProperty`; a stack Wynntils has not annotated, or a definition the live report does not name, stays Wynncraft's. The step runs before the stubs: ingredient rows parent these models, and a stub is written only if its parent resolves.
- **Outlined icons** (`outlined_icons`). `OutlinedIconStep` redraws an icon's art with a dark outline (`PixelDrawing.outlined`) as a generated item at `vetsmod:retro/icon/<type>`, at the size its group gives. `gear_box_icons` supplies the type with no flat art (the Allegiance tome's shield). The icon's item definition is named by the live report, so art that has gone draws no missing model.
- **Block models** (`block_models`). A block model Wynncraft remakes is written as a stub of another model; vetsmod's own wall candle stands where vanilla's wall torch does.
- **Stack models** (`stack_models`). Stacks a model stub cannot reach (a vanilla splash potion Wynncraft leaves alone, an item sharing its model). `RetroItemModelResolverMixin` hands each stack's item model to `RetroStackModels`, which asks `RetroAccessories` first, then looks the rows up by item model and reads the name only of a row's item. The stack keeps its component.
- **Models that parent a stubbed model** inherit the stub. The report lists them (§9).

## 6. The UI

- **Containers.** `same_name` copies vanilla's `gui/container/*` over the ones Wynncraft repaints. The titles, glass and hover rules that make those screens read as vanilla's are the semantic layer's (§7).
- **Inventory edits** (`image_edits`). Rectangles painted a sampled colour over a copied texture (the inventory's crafting grid and offhand slot). Each fill has a palette guard (`PixelDrawing.fill`): the rectangle may hold only the listed opaque colours, or it is left alone and the report says the layout changed. A texture with edits is always emitted. The report records each painted rectangle (`RetroReport.imageEdits`), and `LivePack.imageEdits(textureId)` answers them while the pack is live, so the hover rule makes inert only the slots a fill really covered. `lang` never restores "Crafting".
- **Tooltips.** Every Wynncraft tooltip style is aliased to vanilla's `tooltip/background` and `frame`, which `same_name` restores with their nine-slice `.mcmeta`.
- **Copies of Wynncraft's textures** (`wynncraft_copies`). Before a rule replaces it, the generator copies a texture as the reload shows it without retro, with its `.mcmeta`, to a `vetsmod` id. A copy hides nothing, and the report records each (`RetroReport.wynncraftCopies`). Two uses beside the tier layer's Wynntils tag: the **container backgrounds** (`LivePack.wynncraftCopy`: a screen that keeps Wynncraft's label is drawn on Wynncraft's own background again, §7), and the **LEGACY border** (the copied `unique` sprites are the tooltip style `vetsmod:legacy`; `LivePack.isLegacyTooltipStyle()` is true while the pack is live and both sprites were written, and `LegacyItemHandler.legacyBorder()` then answers it, so legacy items keep the gold border whether retro is on or off; [project_legacy_items.md](project_legacy_items.md) §8).
- **Copies of the sources' textures** (`source_copies`). A texture copied from the first source that has it, with its `.mcmeta`, to a `vetsmod` id, for art a stub needs at an id of its own because a rule keeps the original or it lives in a folder no item atlas takes, and for the overhealth hearts `RetroHud` draws by id; the atlases stitch each copy as any pack's texture. A row is a texture, or `{<recipe>: '#RRGGBB'}`. A copy no source has is reported and skipped, and a stub that needs it is skipped too; a heart with no copy would draw as the missing sprite, which is why `ShippedAssetsTest` pins each one's source in the jar.
- **Wynntils' textures** (`wynntils_textures`). Wynntils loads these as plain textures. Each is drawn again at the live texture's size: fully transparent, or a vanilla panel nine-sliced from a region. A missing live texture, or a height the frames cannot share, is reported.
- **Blank textures** (`blank_textures`). Wynncraft's art written fully transparent at its own size, where vanilla's goes and no row of its own takes it out. It runs after the texture rules, so it outranks their file.
- **Language** (`lang`). The static files restore vanilla's `container.inventory`, `menu.returnToGame` and `menu.game` in the five English locales Wynncraft overrides. "Inventory" belongs on the vanilla containers retro relabels; on a container that keeps Wynncraft's label the semantic layer blanks it again (§7).
- **Empty armour slots.** Wynncraft fills an empty armour slot with a placeholder item drawn as its orange silhouette, and blanks the slot's own silhouette sprite. An alias draws the placeholder as vanilla's grey silhouette and `same_name` restores the sprites.
- **The HUD's sprites.** Wynncraft blanks vanilla's hearts, food and experience bar and repaints the hotbar under its ornate frame. `same_name` restores, from vanilla, the sprites retro's HUD draws; each beats the automatic keep of a blank.
- **Kept on purpose.** Wynncraft's other GUI sprites stay: the other slot silhouettes, boss bars, and its other HUD blanks that retro draws nothing new with.

## 7. Drawing over the screens

A pack can change what a texture looks like, not what a screen does with it: Wynncraft's containers draw their ornate art through their title glyphs, and some of their slots are buttons. The parts below run only while the retro pack is live and the part of retro each belongs to is on (§13). Each class under `retro/render` draws through a `RetroGuard` (catches every `Throwable`, logs the first failure at warn and later ones at debug; a stopping guard then runs nothing more until restart, a retrying one goes on), and after a failure the screen draws as if retro were off, but for the HUD, whose replaced elements then draw nothing (its bullet below). The legacy highlight is `LegacyHighlightPainter`'s, outside `retro/render`, and has no guard of its own. A guard is not the reload's no-throw machinery, which protects the player's packs. `IdentityMemo` and `WeakIdentityMemo` (keyed by a screen) cache a value per key by identity; `RetroStacks` builds the decorative stacks on first use.

- **Titles** (`container_titles`, `glyph_titles`; `RetroContainerTitles`). `RetroContainerTitleListener` hands each container label to `relabel`. Each screen is decided once, at whichever comes first of its background and its label:
  1. the first `container_titles` row matching the simple name of the screen's Wynntils container class: its title, or `keep`;
  2. otherwise the readable title (`readableTitle`): the runs in the default font, without formatting codes, private-use glyphs and unassigned characters, spaces collapsed, except in a title of two words at least four spaces apart (a player trade's, `TWO_SIDES`), which keeps them so each name sits over its side; none without a letter or digit;
  3. otherwise a `glyph_titles` row of a glyph in the title, counted in Wynncraft's `interface` font alone since other fonts reuse the code points;
  4. otherwise Wynncraft's label.

  Only the drawn label changes; `screen.getTitle()`, which Wynntils and the rest of the mod match against, is untouched. Dropping the glyph label drops the ornate background it drew, which leaves the vanilla chest. The decision records the screen's class, title, Wynntils' bounds and whether it is a Wynntils full-screen view. Each fallback decision is logged at debug once per title (`Retro title: ...`), so a screen whose art matters can be given a `keep` row. The player inventory's label comes next (`relabelInventory`): kept where retro drew the container's label, blanked where the screen keeps Wynncraft's and on a full-screen view retro relabels (the content book), whose lower part holds Wynncraft's buttons.
- **Backgrounds** (`RetroContainerBackgroundMixin` on the texture argument of the `renderBg` blits of `ContainerScreen`, `HopperScreen` and `AbstractMountInventoryScreen`). A screen that keeps Wynncraft's label is drawn on the pack's copy of Wynncraft's texture (`LivePack.wynncraftCopy`), so Wynncraft's glyph art sits on the texture it was made for; any other screen draws the texture as it is. Wynntils' full-screen views have glyph-only titles, so they keep Wynncraft's label and background unless a row draws one.
- **Slot fills** (`slot_fills`; `RetroSlots`). Applied on the inventory screen and on a screen whose label retro drew, never on one that keeps Wynncraft's label, nor on a Wynntils full-screen view (Wynncraft fills its player-inventory part with its own buttons). A **panel slot** is one a row picks: `{player: wynntils}` is the player's slots Wynntils names, matched by the slot's own inventory and index there, never the menu index; a container row picks a chest's slots by `rows`, `cols`, `slots` (numbers or `'a-b'` ranges), `outside_bounds` or `all`, never one in its `except`; `unless` skips a container; `fallback: true` makes a row apply only where no earlier row did. A picked slot shows vanilla's white stained glass pane (`RetroStacks.whiteGlass`) under its item, its frame still in sight, since its item cannot be moved; with nothing, or Wynncraft's filler (a hidden tooltip, or a name with no letter or digit), it also answers no mouse. An accessory slot stays a plain slot and always answers, with a two-pixel white edge along its bottom (and down the last one's right). `RetroSlotListener` (`SlotRenderEvent.Pre` at `HIGHEST`, `receiveCanceled`) draws the glass before the slot's item, so the item, Wynntils' highlights and vetsmod's legacy highlight lie over it. A screen's panel slots are worked out when it is first drawn and again when its title decision changes. A failure drawing a slot costs that slot that frame. The slots a row excepts are the ones the player sets (the Trade Market's item, price and quantity).
- **Hover** (`RetroSlots.hovered`, from `RetroHoveredSlotMixin` on `getHoveredSlot`, only on Wynncraft). No slot answers the mouse over an inventory slot whose square lies wholly inside a rectangle the live pack's `image_edits` painted, nor over an empty panel slot that is not an accessory slot: no highlight, no tooltip, and a click lands on the glass. A panel slot holding an item and every accessory slot still answer. A failure here stops this rule until the game restarts, so every slot answers the mouse; `/wv retro off` then `on` does not bring it back.
- **The legacy highlight.** While the pack is live, `LegacyHighlightPainter` draws legacy slots as an outlined circle in the configured foreground colour, with no gradient; the saved settings are untouched.
- **Slot values** (`slot_values`; `RetroSlotValues`, called from `RetroSlotListener` after the slot's item). Wynncraft prints some values in a container's title over a button it draws as nothing, and retro's title drops them. The value is read from the button's lore by exact item name (not slot number) and drawn centred in its slot, on containers retro relabels only.
- **Gear box and tome icons** (`gear_box_icons`, `outlined_icons`; `RetroSlotIcons`, fed by `RetroSlotIconListener`). Every gear box is one chest (§5), so the listener draws the box's type over it on `SlotRenderEvent.Post` and `HotbarSlotRenderEvent.Post`, where Wynntils' own `UnidentifiedItemIconFeature` draws its icon. A stack Wynntils reads as a `GearBoxItem` gets its type's icon: the generated outlined item if `outlined_icons` has the type, else the real vanilla item from `gear_box_icons` through `renderFakeItem` (named by the pack's copy of vanilla's item definition while the live generation wrote it, else the plain item). A `TomeItem` is the glinting enchanted book with its type over it; the Ability Tree button (`AbilityTreeItem`) is the glinting book alone, and only on a screen retro relabelled.
- **The attack-speed effect** (`hidden_inventory_effects`; `RetroInventoryEffects`). Wynncraft shows a weapon's attack speed as an endless haste or mining fatigue. `RetroEffectsInInventoryMixin` filters what the effect list reads: an effect whose id a pattern matches is left out only while it lasts forever, so a haste that runs out still shows.
- **The HUD** (`RetroHud`). Wynncraft never moves vanilla's health or food with its own, so vanilla's HUD is drawn from Wynntils' values. `RetroHud.register()` (from `onInitializeClient`, since Fabric takes HUD elements before the client has started) replaces vanilla's elements through `HudElementRegistry.replaceElement`: `HEALTH_BAR` ten hearts from `Models.CharacterStats.getHealth()` (poisoned while `Models.Ability.corruptedBar` is active), and health above its maximum as overhealth: the same row fills again from the left, a full row per maximum and at least one half, in orange over the red, then yellow, then green, which caps it at four times the maximum (`source_copies` hearts, vanilla's own recoloured, at `RetroAssetIds.overhealthTexture`; they draw over poisoned hearts unchanged); `FOOD_BAR` and `MOUNT_HEALTH` ten shanks from `getMana()`, filled from the right; `INFO_BAR` the experience bar from `Models.CombatXp` plus the combat level as vanilla's green number, when vanilla draws its experience bar this frame (`GuiAccessor` reads `Gui.contextualInfoBar`; the locator and a mount's jump bar stay vanilla's); `EXPERIENCE_LEVEL` nothing. A row is twenty halves filled as the value's share of its maximum, rounded down but at least one half while anything is left, so it shows any loss. Values are drawn only in a world and once Wynntils has read them. No height is registered with `HudStatusBarHeightRegistry`: a registered one makes Fabric move the action bar, where Wynncraft draws the rest of its HUD. `RetroActionBarListener` takes out of the action bar, through `RetroHud.hideWynncraftsBars` and `setSegmentEnabled(<segment>, false)`, what Wynncraft draws in those places: the health and mana bars, the ornate hotbar frame, the experience bars and the level badge with its animations and ultimate charge. The health and mana numbers, the spell inputs and the ultimate's "F" prompt stay. The HUD is drawn while the pack is live and the game is on Wynncraft; a failure there stops retro's HUD for the session, and the replaced elements then draw nothing and the action bar is left whole.
- **Wynntils settings** (`wynntils_config`; `WynntilsConfigOverrides` over the `WynntilsSettings` seam, `LiveWynntilsSettings` the production form). Settings are written as `/wynntils config set` takes them, found as Wynntils' `ConfigCommand` finds them and read with `Config.tryParseStringValue`; one that is missing, or whose value does not parse, is skipped with a warning, never `setValue(null)`. They follow the setting, not the live flag:
  - **On** (`/wv retro on`, at start-up while on, and when the parts change): only a setting whose part is on is switched, and a saved one whose part has gone off is put back. A setting the snapshot has no entry for is saved first (its value as text, and `userEdited`); the snapshot is written to `retroWynntilsSnapshot` before anything changes; then each setting is set and Wynntils' config saved. A setting whose value cannot be written back as text is never changed. A snapshot that survived a crash already holds the player's values, so it is never taken again.
  - **Off** (`/wv retro off`, `CLIENT_STOPPING`, the latch, and start-up while off with a snapshot left over): each saved setting that still has retro's value goes back, by `setValue(original)` or `reset()` when the player had never set it; one the player changed since stays theirs. The snapshot keeps only the settings that could not be found, read or set, so the next start-up or `off` tries again. Putting them back at every close leaves the Wynntils file the player's own after a normal close; after a crash they stay until vetsmod next starts.
  - **Start-up** waits for Wynntils, which loads its features at the end of the first resource reload: a client tick registered at `CLIENT_STARTED` checks until `Managers.Feature.getFeatures()` is not empty. Every Wynntils call is guarded.
  - `/wv debug trigger retroDump` lists the switched settings, read from the snapshot.

## 8. Accepted trade-offs

- **Player packs.** In preloaded sessions the retro pack sits directly above Wynncraft's, so a pack the player put above Wynncraft's still wins, but one below it loses to retro's copies. In the first session after a Wynncraft update, Wynncraft's pack is a server pack at the top, so retro sits above every player pack too.
- **About a hundred textures fall through to modern vanilla** because 1.21.11 Programmer Art lacks them (dirt, wool, chests among them).
- **Models that parent a stubbed model** inherit the stub: climbing gloves draw as shears, a hobby horse as an iron shovel, chainshots as a bow, `archaic_writing` as paper. Keeping their art would need an edited copy of Wynncraft's model, which the design rules out. The report lists them.
- **Leather chestplate and leggings icons.** Programmer Art 1.21.11 has the 2013 leather pieces but no `leather_chestplate_overlay` or `leather_leggings_overlay`, so those two icons draw today's vanilla overlay over the 2013 piece, as Programmer Art itself does in game. Worn leather is whole.
- **The gear boxes' chest is today's vanilla chest.** Programmer Art 1.21.11 has no `entity/chest/normal`.
- **Particles are out of scope.** Wynncraft's spells and combat draw sprite effects from its particle textures, so `keep_wynncraft` keeps every `particle/` texture.
- **Glass and hover.** The pane is drawn before the item, so the back half of the hover highlight lies under it on a glazed slot that holds an item.
- **Wynntils settings follow the setting, not the pack.** They stay switched while retro is on but stopped for the session, and a setting the player changes by hand while retro is on is kept at the next close but switched again at the next start-up.
- **The level badge's other readouts.** The badge goes because the vanilla level number and experience bar take its place, and with it what it shows besides the level: sprint and breath on its rim and an ultimate's charge in its middle. Vanilla's air bubbles stay Wynncraft's blank. If they are missed, retro could draw them itself (Wynntils keeps only sprint, `Models.CharacterStats.getSprint()`).
- **The experience bar is combat's**, throughout, though Wynncraft's shows the profession's while gathering.
- **Wynntils' unidentified-item marks.** Turning `UnidentifiedItemIcon` off also hides the "?" it draws on revealed but unidentified gear.
- **Wynntils' content book only with shift.** While retro is on, a plain click or the content book key opens Wynncraft's content book, drawn as a vanilla chest of its entries above Wynncraft's buttons, with no "Inventory" label and no glass; Wynntils' own book needs shift held. Switching the feature off instead would take its key binds with it.
- **One icon for related items**, such as the bowls of soup and stew.
- **Iron ingot's dark edge.** Its two-shade dark edge keeps only the darker shade (`#353535`) undyed; the other recolours.
- **Art an on part draws is replaced everywhere it is drawn.** With only `weapons` on, a Wynncraft ingredient that draws `item/stick` shows the 2013 stick. Isolating them would need vetsmod-namespace copies of vanilla's models.
- **Icons of blocks follow `blocks`.** Many of Wynncraft's item models parent vanilla block models (on pack `a43ae4e6`, those of `only crafting` draw 111 block textures, stone and dirt among them). A block texture is replaced only with `blocks` on, since replacing it for an icon would repaint the world, so with `blocks` off those icons, a ward's stained glass and the `glass` part's pane draw the world's art, and with `blocks` on and `crafting` off an ingredient drawn as stone shows the 2013 stone.
- **A kept screen's background stays registered.** The texture manager keeps a plain texture once drawn and loads it at every reload, so after a screen has been drawn on a copied background each later reload without the retro pack logs `Missing resource vetsmod:textures/gui/container/wynncraft/<name>.png` once. Nothing draws it, and the reload does not fail.

## 9. The report and the item dump

Two debug tools show what the rules did, for whoever edits them. Nothing that draws reads either.

**The report** (`/wv debug tree retro report [ingredients]`, `RetroDebugCommands` → `RetroAudit`; [vetsmod_commands.md](vetsmod_commands.md)). Run it after each Wynncraft update. It writes `report-<yyyyMMdd-HHmmss>.txt` (or `report-ingredients-…`) under `vetsmod/dumps/retro/` and says in one chat line where it went and what it found: `unused_rows`, `ingredient_gaps` (`stems_without_row` with the argument), `derived_models`, `drawn_through_parent`, `equipment_without_row` and `divergent_textures`. It needs the retro pack drawn now. With a part off, the file says so, and the chat line ends `parts_off=<names>`, since the rows still count ids but what they write is left out: read a low count there before suspecting Wynncraft. The generation keeps what it looked at and decided in its `RetroReport` (`Seen`: every texture's decision, the textures Wynncraft ships, the models and equipment assets, the stubs written and the tint factors), so it measures nothing for the report; the audit reads the packs again only for what it says about them, on a thread of its own, one report at a time. Its sections:

- the summary, the counts and the rules the generation skipped;
- every pattern row of the rule files with how many ids it decided (`RuleUsage.of`), the rows that decided none first. A row decides an id when it is the first row of its section to match it, and a section is offered only the ids no section above it took (§4, §5). The screen sections are not checked;
- the ingredient stems with no row whose model parents no vanilla model; with `ingredients`, every stem, with its row, its parent and the Wynntils ingredients whose icon it is;
- the models that parent a stubbed model through any chain (`AuditModels.derived`), and those among them that draw the stub with no art of their own on the way (`drawnThroughParent`);
- each `tints` row with its contrast, the textures it tinted, the source each was read from and its factors;
- the equipment assets Wynncraft ships that no row covers;
- the block textures `same_name` replaced while Wynncraft's art barely resembles vanilla's (`TextureDivergence`: brightness correlation below `DIVERGENT`), for a `keep_wynncraft` row where Wynncraft repurposed a name. The comparison is with vanilla's texture, the art Wynncraft repainted.

**The item dump** (numpad `+` with `itemDump` on, dump format 4) adds `vetsmodAnalysis.retro` (`HoverDumps.buildRetroDump`): `packLive`; the stack's `itemModel` and `customModelDataFloat0`; `wynntilsItemType`; and the `models` its live item definition draws for it in an inventory, each with the `pack` that provides it now (`vetsmod/retro` once a stub replaced it), the `rule` that stubs it and the `art` that stub draws. The `rule` is what the rule files say whichever parts are on, so with a part off a model's `pack` can be Wynncraft's beside a `rule`. Minecraft keeps only baked item definitions, which no longer name their models, so `LiveItemModels` reads the definition (`items/<item_model>.json`) from the loaded resources, parses it as Minecraft's loader does and walks it with the stack: a composite draws every part, a condition, select or range dispatch the branch the stack picks. Parsing costs as much as the file is long (Wynncraft's `items/potion.json` is about 1.5 MB, an `oak_boat` stack's `items/oak_boat.json` about 8 MB), so the dump parses on a background worker, walks back on the render thread and writes the file there.

## 11. How to add

Each recipe runs: find it, add the row, pin it, check it. Find: numpad `+` item dump, `vetsmodAnalysis.retro.models`, or `/wv debug tree retro report`. Check: the report's unused-row and skipped lines. End every recipe by adding or updating the test entry in [vetsmod_tests.md](vetsmod_tests.md).

- **A material** (an ingot, gem, grain, fish, plank): add `name: '#RRGGBB'` under the recipe of its family in `materials`, or `name: 'minecraft:item/x'` under `vanilla`. A new family is a `models` prefix plus rows. The row expands to a `source_copies` copy and an `item_models` row. Pin: `ShippedItemModelsTest` (a pinned model per family).
- **A bucket colour** (an oil): a name under `bucket:` in the `oil` family. It tints only the water pixels (`hue_of`).
- **A new recipe**: a `recipes` row `name: {art}` for grey art a colour multiplies, or `name: {art, scale_from | hue_of}` for coloured art; name it after its art. `potion_overlay` is the one name code reads, for every potion's liquid.
- **A content book activity**: a row of `activities` in `content_book_activities`, the name to its art. It makes the active row and a copy and row per state. Pin: `ShippedItemModelsTest` works its count out from the table, so nothing else changes.
- **An item row**: an `item_models` row, `'<model pattern>': 'minecraft:item/x'` (flat), `{texture, parent}` (held as handheld, handheld_rod, bow or generated) or `{model: id}` (a vanilla model whose tint must survive). A table family: a pattern is one literal id. Pin: `PINNED_MODELS` in `ShippedItemModelsTest`.
- **A stub for an ingredient**: a `retro_ingredients.yml` row, or no row and an `item_models` row; `keep` to leave Wynncraft's. A shield is drawn by `stack_models` with `keep`.
- **A potion family**: a `potions` row with the liquid colour (and Avomod's model name). Pin: `ShippedPotionsTest`.
- **A tint**: a `tints` row with `source` and `tint` (colour, `match`, `relative_to`, `auto` or `like`), optional `strength` and `contrast`; the texture must be a block texture in the jar. Pin: `PINNED_TINTS` in `ShippedTexturesTest`.
- **A replaced texture**: a `same_name` pattern, or an `aliases` row to another id; a `keep_wynncraft` row if Wynncraft repurposed the name. Pin: `PINNED_VARIANTS` in `ShippedTexturesTest`, or a decision test.
- **A recoloured copy for a stub**: a `source_copies` row `'vetsmod:...': {recipe: '#RRGGBB'}`, then an `item_models` row at that id.
- **A GUI sprite**: a `source_copies` row at `vetsmod:gui/sprites/<path>`, drawn from code as `vetsmod:<path>`, with the id in `RetroAssetIds`. Pin: `ShippedAssetsTest`, as `everyOverhealthHeartIsACopyOfVanillasHeartOfItsFill` does.
- **Worn armour**: an `equipment` row to a vanilla asset or `keep`. Pin: `ShippedEquipmentTest`.
- **A generated icon**: for a flat icon with an outline, a type under a group of `outlined_icons` (art, group scale and outline); for the real vanilla item, `gear_box_icons`. An accessory type or tier: `accessory_tiers`.
- **A screen's title**: a `container_titles` row by Wynntils container class (`keep` for an art-bearing screen); for a glyph-only screen with no class, a `glyph_titles` row by its font glyph.
- **A screen's glass**: a `slot_fills` row; add the screen to the fallback row's `unless` when its empty slots take items. Pin: `ShippedScreensTest`, `RetroSlotsTest`.
- **A value on a blank button**: a `slot_values` row. **A single stack by name**: a `stack_models` row. **A block model**: a `block_models` row (vetsmod's own under `block/retro/`). **A Wynntils setting**: a `wynntils_config` row, as `/wynntils config set` takes it. **A Wynntils texture**: `wynntils_textures`. **A texture a rule replaces but something still needs**: `wynncraft_copies`, read through `LivePack`. **A panel edit**: `image_edits` with its palette.
- **A section**: add its constant to its family in `retro/manifest/`, and put it in the family's `NAMES`, `parse`, `addCounts` and component list; give the header of `retro_textures.yml` its format.
- **A generation rule**: one `GenerationStep` class plus one entry in `RetroPackGenerator.STEPS`, whose order is behaviour (a step that writes what a stub names comes before the stubs). Add a `RetroReport.Count` value for what it writes, which the summary line and the report's counts then show, and a row in the §3 table for its section. A new top-level folder also goes in `RetroPackResources.FOLDERS`, after checking nothing reads it on the render thread. Test it in `GenerationStepsTest`.
- **A generated id**: spell it once in `RetroAssetIds`.
- **A part**: a constant in `RetroPart` and a row of `parts` in the same place in its order, with its `about`. It owns ids by patterns above the catch-alls of `items`, and what it draws from code by `RetroModeManager.isPartLive`. Pin: `ShippedPartsTest`, whose first test fails until the row is there.
- **A row of a new kind goes to a part**: an item model, texture or Wynntils feature with a new prefix falls to `items` or to no part, so give it a pattern under the part a player would expect, and a stack row its `part`. A section that writes into `minecraft:` or `wynntils:` needs `PartFilter` in its step (§13). Pin: a sample in `ShippedPartsTest`.

## 13. Parts

Retro is split into named parts, each on by default; `/wv retro on|off` stays the master switch, and `/wv retro parts <part|all> <on|off>` and `/wv retro only <part>` choose among them. The table is `retro_textures.yml`'s `parts` section, whose rows say what each covers and own ids by patterns. A part off looks as if retro were not installed, as far as shared art allows. With every part on, no model is walked and every generated file is what the rule files decide.

**State.** `retroPartsOff` holds the names of the parts turned off, so a part a later version adds is on for everyone and a name this version does not know is ignored ([vetsmod_config.md](vetsmod_config.md)). `RetroPart.parseOff` and `formatOff` are the stored form. `RetroModeManager.partsOn()` reads the setting once into an immutable set, which only `setPartsOff` changes, because a slot asks every frame. `isPartLive` and `isPartLiveOnWynncraft` are `isPackLive` and `isLiveOnWynncraft` for one part. `setPartsOff` stores the choice, applies the Wynntils settings again while active and reloads when a retro pack is loaded; with none, the next reload reads the setting.

**Decisions** (`PartFilter`, pure). The first row in file order with a pattern matching an id owns it; an id no row owns cannot be turned off. `TextureRules` and `ModelRules` do not know of parts, so the report and the item dump still read what the rule files say. `blocks` comes first, so it takes the block entities' `entity/` textures (signs, beds, banners, chests, the enchanting table's book, shulker boxes, whose folder the shulker shares) from `mobs`. `accessories` owns no id: it is what `RetroAccessories` draws, and an empty accessory slot's placeholder is `screens`', as an empty armour slot's is. The content book is one `item_models` row for `player/content_book` and `gui/player/content_book`, so `items` owns both.

**Shared art** (`DrawnArt`). `minecraft:item/*` textures are drawn by more than one part: a spear's stub draws `item/iron_shovel`, owned by `items`, and most of Wynncraft's ingredient models parent a vanilla item model, whose `item/gold_nugget` would be redrawn if `items` being on replaced it. So with any part off, `TextureStep` first walks every model `ModelStubStep` lists:

- on, with a stub: the stub's art (a tint-proof stub's texture, the textures of the model an ingredient's or model stub parents, a potion's bottle) goes to `on`;
- on, with no stub: the textures its own model draws go to `on`;
- off: the textures its own model draws, which is what will show, go to `off`.

A model's textures are its slots, each its own over its parents' through the `parent` chain, read from the reload's packs top first, with `#` references followed and `particle` left out, since a slot or a hand does not draw it (`ModelJson.read` and `drawn`, which `StubWriter` reads with too). What an on part draws by code joins `on`: `gear_box_icons` and the glinting book with `gear_boxes` on, and `stack_models`' targets with their row's part on. Each is read from vanilla's item definition, so every model it can pick counts (the clock's 64 frames, there being no `item/clock` model), and a shield adds `RetroAssetIds.SHIELD_ART`, which its special renderer draws and no model names, though `mobs` owns it. `PartFilter.textureOn` then writes a texture `blocks` owns only with `blocks` on, and any other when `on` has it, or when its owner is on or it has none, unless that owner is `items` and `off` has it. A copy or tint that fails this becomes `Keep(PART_OFF)`, counted as `parts_off`, with no skipped line, and an `image_edits` row of it adds none either, so `LivePack.imageEdits` is empty and the hover rule drops by itself.

**Generation.** `GenerationContext.parts` is read once per generation. `ModelStubStep` and `BlockModelStep` skip a model that is off (`ModelStubStep` still lists it), `EquipmentStep` replaces nothing with `armour` off (still listing each asset), `BlankTextureStep` and `WynntilsTextureStep` skip a texture that is off, and `staticFiles` answers no language files with `screens` off. `source_copies`, `wynncraft_copies`, `outlined_icons`, `accessory_tiers` and `gear_box_icons`' item definitions write only into vetsmod's namespace, which hides nothing, so they are always written and what draws them gates instead. The report's `partsOff` says which were off.

**Drawing.** `RetroHud.mode`: `hud` off is `Mode.VANILLA`, and the action bar stays whole. `RetroContainerTitles`: `screens`; with it off a screen is never relabelled, so everything that asks `relabelled` answers as for a screen that keeps Wynncraft's label, without its copied background. `RetroSlots`: `glass` picks the rows, and without it the slots `image_edits` painted stay inert. So `glass` works on the inventory without `screens`, and on a container needs it. `RetroSlotValues`: `screens`. `RetroSlotIcons`: `gear_boxes` for boxes and tomes; the Ability Tree's glint keeps its relabelled test. `RetroStackModels`: `RetroAccessories` with `accessories` on, and each `stack_models` row with its part on. `RetroInventoryEffects`: `effects`. `LegacyHighlightPainter`: `highlights`. `WynntilsConfigOverrides.apply()` passes only the rows of an on part, so its "a saved setting the rows no longer change is put back" restores a part turned off.
